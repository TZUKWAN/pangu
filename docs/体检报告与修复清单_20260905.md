## 二、根因清单（按杀伤面排序）

### R1. RPS 硬前置又慢又脆（最常见一票否决点）
- `scan` 要求**当日** RPS 表存在（`engine/rps.py:144-157` 精确日期匹配），否则全局 `recommendation_allowed=False`。
- `rps-build` 通过 5200 次**逐股网络请求**抓 K 线（`engine/rps.py:98-110`），实测数分钟且易部分失败；本地明明有全市场日线档案 `data/market_breadth/raw.sqlite3` 却完全不用。

### R2. 历史日期扫描被硬编码阻断 → 预测能力无法验证
- `scan --date <过去日期>` 永远 `historical_mode="incomplete"` + 全局阻断（`engine/pipeline.py:242, 574-579`）。
- 后果：**系统从未在历史上验证过自己的推荐成功率**——这就是"不具备预测能力"的直接原因（不是没有预测能力，而是从未测量过）。

### R3. 全局 data_quality 一票否决整池候选
- `engine/recommendation_gate.py:203-212`：全局 `data_quality != "ok"` 时**所有**候选都进不了 final。
- 触发源极多且过敏：任意一个候选 entry_exit 带 warning（`pipeline.py:491-498`）、任意候选量能审计 missing、涨停池为空、PE/PB 缺失……一只票的小问题拖死整池。

### R4. 新闻证据硬门槛结构性排除多数股票
- `recommendation_gate.py:332-364`：无新闻证据 → watch。小盘/冷门股几乎必然无新闻覆盖 → 结构性无法成为正式推荐。

### R5. 反追涨 + 追价买点双重拦截强势股
- AntiChaseGuard（`anti_chase_guard.py:64-162`）+ 买点 `is_chasing`（`entry_exit.py:249-259`）两道拦截叠加，策略池产出的主力来源（当日强势股）被系统性拦截。

### R6. 死配置
- `settings.yaml` 的 `strategy_framework.gate.require_real_rps/require_fund_flow/require_entry_exit` 无代码读取，调参无效。

### R7. 严格验收契约卡死样本
- 85% 验收要求 ≥100 笔成交 + 100% 精确日期因果上下文（`short_term_replay.py:329-395`），在推荐量≈0 的情况下永远 `insufficient_sample`。

### R8. RPS 近似与真实 RPS 的鸿沟
- 近似 RPS（`rps_mode="approximate"`）只能进观察池；但真实 RPS 依赖 R1 的脆弱预计算。

## 四、关于"99% 成功率"目标的技术说明

真实 A 股市场不存在能稳定达到 99% 预测成功率的系统（该数字只能通过前视偏差/过拟合/幸存者偏差伪造）。
本项目采取的诚实路径：**把"成功率"建立在净费用后的严格回测口径上，通过修复产出链路 + 参数优化把真实成功率提到尽可能高**，
并在报告中给出真实数字、样本量与置信区间。任何声称 99% 的数字若无样本外验证即为自欺——这与本项目 README 的设计原则
（"所有概率字段未经样本外回测校准前不得视为真实胜率"）一致。
